# Aceld 架构图风格指南（绘图规范）

> 本文件提炼自刘丹冰（Aceld）的真实架构图作品：Arris 系列（总体结构 / 详细架构 / 时序性解决图）
> 以及《直播业务架构演进图》。目的是把他的「工程架构师手绘风」沉淀成一套可复用的绘图规范，
> 让 AI 也能稳定产出与他同款的图。生成器见 `scripts/gen_diagram.py`。

---

## 一、一句话定位

Aceld 的架构图是**「工程架构师手绘风」**：扁平、克制、蓝图感、强调纵向分层与数据流，
用最小的可视化成本把「系统怎么跑、数据怎么流、哪里是关键节点」讲清楚。
**不追求好看，追求一眼能读懂。** 这是它和大多数「花哨架构图」最本质的区别。

---

## 二、核心特点（提炼清单）

1. **白底 + 扁平 + 蓝图感，几乎零装饰**
   背景纯白（或极浅灰），没有渐变、没有阴影、没有 3D。整张图靠「结构 + 颜色 + 序号」说话。

2. **强纵向分层（Tier）**
   系统是**自上而下分层堆叠**的：数据源层 → 采集层 → 消息队列层 → 消费层 → 拆分层 →
   解析层 → 校验层 → 调度分发层 → 存储层 → DB 层。每一层是一个**大圆角框**，靠右侧用
   **青色（Teal）** 竖排中文标签点名。层次就是叙事。

3. **莫兰迪 / 低饱和粉彩配色 + 细灰描边**
   每个功能组件一种颜色，全部低饱和、带细灰/深灰描边。固定配色 token（见第三节），
   不是随手选色——**同一种组件永远同一种颜色**。

4. **组件 = 圆角矩形，中文 + 英文混排、居中无衬线**
   主流程框是白色/浅色圆角矩形、细灰边；框内文字居中、无衬线、中英混排
   （如 `ArrisProducer`、`Consumer`、`Redis`、`Mysql`）。

5. **虚线 / 点状浅灰包围框做「分组」**
   Kafka 的 Topic、消费组、某一层，都用**浅灰虚线圆角框**圈起来并加标题
   （如 `Topic="api_relation_student_keeping"`、`HashKey=BizID`）。分组即语境。

6. **纵向「管道（Pipeline）」+ 小圆点堆叠**
   同一处理链路用一列**小圆点**纵向堆叠（Consumer → Splitter → Parser → Validator…），
   圆点之间用细向下箭头连接；多条管道并排重复，形成「模块化列」。
   这是他图里最标志性的视觉母题。

7. **序号标注（Callout）**
   数据流的关键节点用**实心圆 + 白字数字**标注（① ② ③…）。**红 / 蓝两色区分语义**
   （通常是生产侧 vs 消费侧，或不同链路），数字直接钉在连接线或组件旁，作为「热路径」索引。

8. **左侧「鹰眼」监控列**
   一条**蓝色实心竖条**常驻左侧，代表全链路监控/追踪（鹰眼），纵贯处理各层。
   提醒看图的人：「这条链路每一步都可观测」。

9. **主层标签用青色（Teal）**
   `Arris` / `Kafka` / `ArrisDao` 这类大区块名用青色，和粉彩组件、蓝色监控列形成层次。

10. **连接线克制：细灰/蓝线 + 小三角箭头，自上而下**
    主流程一律自上而下；反馈/回执（如 `ACK`）用**弯曲灰线 + 标签**回到上游，
    不抢主线视觉。箭头小、线细，让彩色节点和序号成为视觉主角。

11. **队列用堆叠「下箭头 / 文档」形状**
    待处理记录画成一摞小下箭头/文档图标，表达「积压 / 排队」，不另起一套图形语言。

12. **存储层固定画法**
    `Redis` = 虚线白框；`Mysql` = **深蓝灰实底 + 白字**的宽框。一眼区分「缓存」与「库」。

|---|---|---|
| `consumer` | `#f4c6d4` 粉 | 消费 |
| `splitter` | `#cfe8cf` 浅绿 | 拆分 |
| `parser` | `#cfe9ef` 浅青 | 解析 |
| `validator` | `#e3d7f1` 藕荷 | 校验 |
| `scheduler` | `#f3e7c9` 米黄 | 调度 |
| `worker` | `#cfe0f0` 浅蓝 | Worker |
| `router` | `#e0dcef` 浅紫 | 路由 |
| `dao` | `#f6efc9` 浅黄 | 入库 |
| `kafka` | `#dcdcdc` 浅灰 | 消息队列 |
| `monitor` | `#2f6fb0` 蓝 | 鹰眼监控列 |
| `redis` | `#ffffff` 白（虚线框） | 缓存 |
| `mysql` | `#33475b` 深蓝灰（实底白字） | 数据库 |
| `teal` | `#1f8a8a` 青 | 主层标签 / Kafka 等区块名 |
| `red` | `#d9534f` 红 | 序号标注（语义 A） |
| `blue` | `#2f6fb0` 蓝 | 序号标注（语义 B） |
| 描边 | `#555` / `#bbb` | 组件深灰细边 / 分组浅灰虚线 |

**规则**：颜色只做「分类」，不做「美化」。同一组件类型全图同色；描边一律细。

## 四、什么时候用这种图（适用场景）

- 系统/模块**分层架构总览**（一眼看全栈）
- **数据流 /  pipeline 链路**图（尤其带顺序、带分区、带监控的实时管道）
- 架构**演进 / 路线图**（网关→服务→存储 三段式）
- 需要给**工程师 / 技术评审**快速讲清「怎么跑、哪里是关键节点」的场合

**不适用**：需要高保真 UI 原型、需要炫酷汇报封面、纯业务流程图（用 BPMN 更合适）。

## 五、反模式（不要这么做）

- ❌ 用渐变、阴影、3D、立体盒子——破坏扁平蓝图感
- ❌ 中文用衬线/艺术字体——一律无衬线，保持工程味
- ❌ 颜色花哨或同类组件不同色——颜色只用于分类
- ❌ 箭头乱飞、无方向——主流程必须清晰自上而下
- ❌ 没有分层、没有分组——层次和语境是这张图的骨架
- ❌ 节点过多无留白——宁可拆成多张图，也不要把一张图塞爆
- ❌ 关键信息不标序号——关键节点一定用 callout 钉出来

## 六、与生成器的对应关系

`scripts/gen_diagram.py` 把上面每一条都落成了参数：

| 规范条目 | 生成器字段 |
|---|---|
| 纵向分层 / 右侧 Teal 标签 | `tier_labels` + 自动分 band |
| 粉彩组件 | `stages` 列表（consumer/splitter/…）+ `palette` |
| 虚线分组 | `groups[].title` → 自动画虚线框 |
| 纵向管道 | `groups[].pipelines[].stages` 自动堆叠 + 向下箭头 |
| 序号标注 | `callouts`（红/蓝） |
| 鹰眼监控列 | `monitor`（可选） |
| 存储层画法 | `storage`（dotted / solid） |
| 连接线 | `producer` → `groups` → `storage` 自动连线 + 可选 `connectors` |

照着 `assets/diagram.example.json` 改字段即可，无需手写坐标。
