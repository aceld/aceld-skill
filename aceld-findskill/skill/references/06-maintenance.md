# 06 · 维护：索引、漂移、体检节奏

> 技能库会烂。烂的方式很固定：来源忘了、版本漂了、重复吸收同一个东西、
> 该淘汰的还在用。这一节就是防腐。

---

## 1. 技能库索引（`SOURCES.md`）

每个技能目录下放一份 `SOURCES.md`，一行一次吸收：

```markdown
# 来源登记

| 日期 | 来源 | commit | 许可 | 吸收内容 | 落到哪 |
|---|---|---|---|---|---|
| 2026-10-31 | anthropics/skills/pdf | a1b2c3d | Proprietary（只读方法） | 先判文本层再 OCR 的顺序 | references/01-script.md §3 |
```

**为什么必须记 commit 而不是只记仓库**：仓库会变。只记 `owner/repo` 的话，
半年后你无法判断"我当时到底看的是哪个版本"。

---

## 2. 版本漂移检查

`vet.py` 的 `--json` 输出里带 `security` 与 `path`，
`absorb.py` 的 `INBOX_REPORT.md` 第 8 节是文件指纹。定期复检流程：

```bash
# 1. 重新拉一份到 inbox（会自动覆盖并重算指纹）
python scripts/absorb.py owner/repo/skill --force

# 2. 比对指纹段
diff <(sed -n '/## 8. 指纹/,$p' 旧报告) <(sed -n '/## 8. 指纹/,$p' 新报告)
```

有差异 → 说明作者改过内容 → **必须重读改动部分**，不能假设"只是小修"。
这是 AST07（更新漂移）唯一的实际防线。

---

## 3. 体检节奏

| 对象 | 频率 | 做什么 |
|---|---|---|
| 正在用的技能（本地 `~/.workbuddy-ai/skills/`） | 每季度 | 跑一遍 `vet.py`，看有没有新的 HIGH 命中 |
| 已吸收的来源 | 每半年 | 比对指纹，看是否需要更新方法 |
| 整个技能库 | 每年 | 删掉半年没用的技能；把重复的合并 |
| 新建技能前 | 每次 | `find.py` 查重：是不是已经有人做过、我是不是要重复造 |

---

## 4. 反重复：吸收之前先查重

吸收冲动最强的时候，恰恰是你已经有一个类似技能的时候。

```
吸收前必问三句：
1. 我现有技能里，有没有哪一节已经在做类似的事？
2. 如果有，是「补强那一节」还是「新开一节」？（默认补强）
3. 如果新开，三个月后我会记得它和旧的那节有什么区别吗？
```

技能库最大的敌人不是"不够多"，是**同一个概念散落在三个文件里，
半年后你自己都分不清哪个是当前版本**。

---

## 5. 淘汰机制

技能也有保质期。满足下面任一条就该删或重写：

- 半年内一次都没用过
- 依赖的 CLI/API 已经改版（跑一遍就报错）
- 被新技能完全覆盖
- 正文超过 800 行且没人愿意读（说明它已经变成仓库而不是技能）

**删除不丢人，留着烂掉才丢人。**

---

## 6. 让技能自己变强（自动体检钩子）

如果宿主支持定时任务，可以挂一个每月体检：

```
任务：技能库体检
1. 列出 ~/.workbuddy-ai/skills/ 下所有技能
2. 对每个技能，用 aceld-findskill 的 vet.py 检查其结构合规性
   （frontmatter 合法、正文 <500 行、引用一层深）
3. 输出一份「该拆 reference 的」「该合并的」「该删的」清单
4. 不要自动改，只出清单
```

关键：**只出清单，不自动改**。自动改技能的风险远大于收益。

---

## 7. 一句话总结

> 技能库的价值 = 被用到的次数 × 判断的准确度 ÷ 维护成本。
> 吸收让分子变大，淘汰让分母变小，登记让准确度可追溯。
