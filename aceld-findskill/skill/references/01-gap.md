# 01 · 缺口判定

> 目的：把「我好像缺个能力」变成一句可检索的缺口描述，并且先判断**该不该搜**。

---

## 1. 四种「不该搜」的情况

搜技能的成本不低（检索 + 读 + 体检 + 改写，半小时起）。下面四种情况直接别搜：

| 情况 | 表现 | 正确做法 |
|---|---|---|
| 现有技能已有流程 | 只是参数没填、路径没换 | 直接跑现有脚本，看 `references/09-pitfalls.md` |
| 是查资料，不是缺能力 | 「XX 库怎么用」「这个 API 参数是什么」 | 用普通检索 / 官方文档 |
| 一次性任务 | 只做这一次，以后不会再用 | 现场写十行代码，别沉淀 |
| 缺口太宽 | 「我要做 AI 视频」 | 继续拆，拆到能一句话说清输入输出 |

**判据**：如果一个能力**至少还会用三次**，或者**每次用都要重新踩一遍坑**，才值得找技能。

---

## 2. 把缺口写成一句话

格式固定：

```
输入：<我手上有什么，什么格式>
输出：<我要得到什么，什么格式，什么质量标准>
约束：<平台 / 语言 / 不能联网 / 必须离线 / 时间预算>
```

对比：

| ❌ 宽 | ✅ 窄 |
|---|---|
| 「找个视频技能」 | 输入：一张 PNG + 一行文案 → 输出：1080×1920 MP4，标题压暗、可循环，ffmpeg 本地跑 |
| 「PDF 处理」 | 输入：扫描版 PDF → 输出：可搜索的文本 + 表格 CSV，中文不丢字 |
| 「写文案的技能」 | 输入：技术博客 md → 输出：小红书 6 张图卡的短句，每页 ≤40 字 |

**窄的缺口能直接变成检索词**：把「输出」和「约束」里的名词抽出来当关键词，
中文搜不到就翻英文（英文技能生态大一个量级）。

---

## 3. 缺口分类（决定搜完往哪放）

| 类型 | 例子 | 搜到后放哪 |
|---|---|---|
| **工具型** | PDF 表单填充、图片去背景 | 现有技能的 `scripts/` 加一个脚本 |
| **方法型** | 代码评审清单、无障碍检查项 | 现有技能的 `references/` 加一节 |
| **领域型** | K8s 排障、税务申报 | 值得做成**新技能**（新目录 + 自己的 SKILL.md） |
| **风格型** | 某种图表风格、某种文案腔调 | 现有技能的 `assets/` 加模板 + `references/` 写规范 |

**方法型最容易被忽略，也最值钱**：别人的脚本你未必能用，但别人的检查清单可以直接变成你的验收 SOP。

---

## 4. 记录缺口（很重要，别跳过）

搜之前先在当前项目的 `NOTES.md` 或技能库里写一行：

```
[缺口] 2026-10-31 竖版视频需要「竖屏版式重排」而非缩放 → 目标：1080×1920 原生布局
```

三个作用：
1. 防止搜着搜着忘了自己要什么（很常见）
2. 搜不到时留下记录，下次直接从这里继续
3. 事后复盘：这个缺口是「真缺」还是「我流程设计错了」

---

## 5. 一个反例

真实发生过的坏路径：

```
需求：做竖版视频
✗ 缺口写成「视频」→ 搜到一堆 ffmpeg 封装 → 都不解决「文字太小」
✗ 又搜「短视频」→ 搜到一堆剪辑/字幕工具 → 仍然不解决
✓ 缺口写成「1920×1080 的 HTML 幻灯片 → 1080×1920 竖屏原生重排（内容区 200–1420px，正文 ≥36px）」
  → 搜「responsive slide layout」「vertical video typography」「mobile-first presentation」
  → 拿到的是版式方法论，正好能吸收
```

**教训**：搜不到往往不是搜索引擎的问题，是缺口写错了。
