# 05 · 吸收与回写

> 吸收不是 `cp -r`。吸收是：读懂它解决了什么 → 用我的约定重写一遍 → 把我的流程变短。
> 如果吸收完流程没变短、验收没变严、判断变清晰，那这次吸收就是失败的。

---

## 1. 吸收五问（写不出答案就别吸收）

在 `INBOX_REPORT.md` 第 6 节逐条写下：

1. **它解决的缺口**，一句话（输入 → 输出）是什么？
2. **它的核心方法**是什么？（不是它调了什么库，是它的**判断顺序**与**检查项**）
3. **哪些能进我的流程**？对应到我哪个技能的哪一节 / 哪个 reference？
4. **哪些必须改写**？（路径、模型、账号、平台约定、语言）
5. **我比它强在哪 / 它比我强在哪**？吸收后我的流程具体变短还是变强了？

第 2 问是关键。绝大多数人只抄第 3 问（功能列表），结果抄来一堆自己用不上的东西。

**例子**：

```
✗ 第 2 问答成：「它用 pypdf 读 PDF，用 pdfplumber 提表格」
   → 这是实现，抄了就是抄代码

✓ 第 2 问答成：「它先判断 PDF 有没有文本层（pdffonts 查），
   有文本层直接抽，没有才走 OCR；表格识别先按横线切，横线缺失才按空白列投影」
   → 这是判断顺序，能迁移到任何语言、任何库
```

## 2. 三种吸收强度

| 强度 | 什么时候用 | 做什么 | 成本 |
|---|---|---|---|
| **借鉴** | 只想要一个点子 | 在 reference 里写一节「做法参考：xxx（来源）」 | 10 分钟 |
| **改造** | 方法对，实现不合 | 按自己的约定重写脚本，保留判断逻辑 | 1–3 小时 |
| **融合** | 填补一个完整能力块 | 重写 + 加验收 + 加进主流程 + 改 SKILL.md | 半天 |

**默认选「借鉴」**。多数时候你需要的只是一个判断顺序或一条检查项，
不需要把人家整个技能搬过来。

## 3. 回写模板

### 3.1 写进 `references/`（方法型）

在对应 reference 末尾加一节：

```markdown
## N. <主题>

> 做法来源：`owner/repo/skill@commit`（<许可>）。仅借鉴其判断顺序，实现为本项目重写。

<判断顺序 / 检查清单 / 反例>

**本项目落地**：`scripts/xxx.py` 的 `yyy()`；验收见第 M 节。
```

**必须写来源**。半年后你会想知道这一节是谁教的，以及它是否已经过时。

### 3.2 写进 `scripts/`（工具型）

```python
"""xxx —— <一句话作用>

做法参考：owner/repo/skill@commit（<许可>）
本项目改写点：
  · 路径从 course.yaml 取，不写死
  · 输出格式对齐 compose.py 的约定
  · 加了 --dry-run
"""
```

### 3.3 写进 `SKILL.md`（流程型）

只在**主流程真的变了**的时候改 SKILL.md。加在「阶段要点」或「铁律」里，
一句话说清新做法，细节指向 reference。

**不要把 SKILL.md 变成摘抄本**——它会挤爆上下文预算。

### 3.4 登记到技能库索引

在 `aceld-skill/README.md` 或技能的 `SOURCES.md` 加一行：

```markdown
| 日期 | 来源 | commit | 许可 | 吸收内容 | 落到哪 |
|---|---|---|---|---|---|
| 2026-10-31 | vercel-labs/agent-skills/web-design-guidelines | 1a2c79d | NONE（只借鉴） | 「按清单逐条核对」的组织方式 | aceld-course/references/02-slides.md §7 |
```

## 4. 冲突处理：别人的做法 vs 我的约定

吸收时最容易打架的三处：

| 冲突 | 处理原则 |
|---|---|
| 目录/路径约定不同 | **永远服从本地约定**。改它的，不改我的 |
| 技术栈不同（它用 Node，我用 Python） | 保留判断逻辑，重写实现。别为了用它引入新运行时 |
| 风格/语气不同（它英文，我中文口语） | 保留结构，重写文案 |

**唯一会让本地约定让步的情况**：它的做法有硬性技术依据（比如「必须用词级时间轴否则漂移」），
而本地约定只是习惯。这时改本地约定，并在 pitfalls 里记一笔原因。

---

## 5. 吸收后的验收（三件事）

1. **跑一遍**：用吸收后的流程完整跑一个小样，确认没坏
2. **对比**：跟吸收前比，时间短了吗？返工少了吗？判断更清楚了吗？
3. **写下来**：如果第 2 步答案是"没变"，**回滚这次吸收**——它在增加复杂度而不产生价值

## 6. 一个完整的吸收例子

```
缺口：竖版视频版式重排（不是缩放横版）

搜到：vercel-labs/agent-skills/web-design-guidelines（安装量 80 万）
     内容：一份 Web 界面规范清单，逐条核对（对比度、点击区、字号、焦点态）

第 2 问（核心方法）：不是「它列了哪些规则」，而是
      「它把设计规范变成一份可逐条勾选的清单，让评审变成执行而非审美判断」

第 3 问（能进哪）：aceld-course 的竖版版式环节 —— 我原来的做法是"看着调"，
      现在改成一份硬清单：正文 ≥36px、内容区 ≤78% 高度、单屏 ≤4 块、
      点击区 ≥44px、对比度 ≥4.5:1

第 4 问（必须改）：它是 Web 通用规范，我要的是竖屏视频；像素阈值、UI 遮挡区全不同

第 5 问：吸收后版式验收从「凭感觉」变成「勾 5 条」，返工从 2 轮降到 0 轮

结论：借鉴（不复制它的规则文本，只借「清单化」这个做法 + 5 条我自己的阈值）
```

注意：**最终落到我技能里的，没有一行是它的原文**。这就是正确吸收。
